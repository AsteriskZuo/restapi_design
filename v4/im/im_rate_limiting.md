# IM API 速率限制指南

## 1. 速率限制概述

IM API 实施速率限制以确保服务稳定性和公平使用。速率限制是 API 常见的保护机制，通过限制单位时间内的请求数量和处理的数据量，防止系统过载、资源滥用和恶意攻击。

## 2. 限制类型

IM API 实施了四种主要的限制类型：

| 限制类型                  | 描述               | 目的                   |
| ------------------------- | ------------------ | ---------------------- |
| RPM (Requests Per Minute) | 每分钟请求数       | 限制 API 调用频率      |
| TPM (Tokens Per Minute)   | 每分钟处理的令牌数 | 限制处理的数据总量     |
| RPD (Requests Per Day)    | 每日请求数         | 限制每天的总请求数     |
| TPD (Tokens Per Day)      | 每日处理的令牌数   | 限制每天处理的数据总量 |

这些限制是并行的，任何一个达到上限都会触发限流响应。

## 3. 统一限制规则

IM API 采用统一的速率限制规则，不区分接口类型，简化了开发者的使用体验。限制仅根据用户等级而变化：

| 用户等级 | RPM  | TPM     | RPD     | TPD        |
| -------- | ---- | ------- | ------- | ---------- |
| 免费用户 | 60   | 40,000  | 10,000  | 1,000,000  |
| 高级用户 | 300  | 90,000  | 50,000  | 3,000,000  |
| 企业用户 | 1000 | 350,000 | 200,000 | 10,000,000 |

这种统一的限制方式具有以下优势：

- 简化开发者理解和实现
- 提高 API 使用的灵活性
- 符合 RESTful API 的无状态原则
- 便于横向扩展和负载均衡

### 为什么选择统一限制而非按业务设置不同限制

我们参考了 OpenAI 等主流 API 提供商的最佳实践，选择了按用户等级设置统一限制，而不是为不同业务端点设置不同限制。这一决策基于以下考虑：

1. **提升开发者体验**：统一的限制规则使开发者更容易理解和规划 API 使用，不需要记忆不同端点的不同限制。

2. **增强资源分配灵活性**：用户可以根据自己的业务需求，自由分配配额到他们最需要的端点，而不受预设的端点限制约束。

3. **简化系统架构**：统一限制使得 API 网关和负载均衡器可以更容易地分发请求，无需考虑特定端点的限制状态。

4. **符合现代 API 设计理念**：REST API 应该是无状态的，统一限制更符合这一原则，因为服务器不需要记住每个端点的状态。

5. **便于动态扩展**：随着业务发展，添加新端点时不需要为每个新端点设计特定的限制规则。

这种方法已在 OpenAI、GitHub 和 Twitter 等大型 API 平台上得到验证，能够在保护系统资源的同时提供良好的用户体验。

## 4. 速率限制响应

### 4.1 HTTP 状态码

当请求超过限制时，服务器将返回：

```
HTTP/1.1 429 Too Many Requests
```

其他错误码, [详见](./im_error_code.md)

### 4.2 响应头信息

每个响应都包含以下限流相关的头信息：

```http
x-ratelimit-limit-requests: 100       # 当前用户的请求上限(RPM)
x-ratelimit-remaining-requests: 99    # 当前时间窗口内剩余的请求配额
x-ratelimit-reset-requests: 1s        # 请求限制重置前的剩余时间

x-ratelimit-limit-tokens: 150000      # 当前用户的令牌上限(TPM)
x-ratelimit-remaining-tokens: 149984  # 当前时间窗口内剩余的令牌配额
x-ratelimit-reset-tokens: 6m0s        # 令牌限制重置前的剩余时间
```

### 4.3 错误响应体

```json
{
  "error": {
    "code": 4290000,
    "message": "请求过于频繁，请稍后再试"
  }
}
```

响应格式，[详见](./im_response_format.md)

## 5. 客户端最佳实践

### 5.1 监控配额使用情况

客户端应主动跟踪响应头中的限制信息，在接近限制时调整请求策略。关键步骤包括：

- 解析每个响应中的限流相关头信息
- 记录剩余请求配额和令牌配额
- 计算距离配额重置的时间
- 在配额即将用尽时采取措施（如降低请求频率）

### 5.2 指数退避重试

当收到 429 状态码时，应实现指数退避重试机制：

- 初始等待一小段时间（如 1 秒）
- 如果重试仍然失败，将等待时间翻倍
- 添加随机抖动，避免多个客户端同时重试
- 设置最大重试次数和最大等待时间
- 优先使用服务器返回的 retry-after 值作为等待时间

### 5.3 请求批处理

将多个小请求合并为批量请求，减少 API 调用次数：

- 收集多个需要处理的项目
- 按合理的批次大小分组（如 10-50 个/批）
- 发送批量请求而非多个单独请求
- 根据剩余配额调整批次间隔
- 处理批量响应并将结果映射回原始项目

### 5.4 主动控制请求速率

根据限制主动控制请求速率，避免触发限流：

- 跟踪当前的请求计数和令牌使用量
- 实现请求队列机制，控制请求发送速率
- 根据 RPM 限制计算请求间隔时间
- 预估每个请求的令牌使用量，避免超过 TPM 限制
- 在配额重置时调整发送策略

## 6. 常见问题解答

### 6.1 如何查询当前配额使用情况？

发送 HEAD 请求到任意 API 端点，查看响应头中的限流信息：

```http
HEAD /api/v1/status HTTP/1.1
Host: api.example.com
Authorization: Bearer YOUR_TOKEN
```

### 6.2 为什么有时即使未超过限制也收到 429？

可能是由于：

- 系统负载保护触发了临时限流
- 您的账户同时触发了其他类型的限制(如 TPM 或 RPD)
- 请求模式被识别为异常行为

### 6.3 限流是按什么维度计算的？

限流按以下维度计算：

- 用户 ID/API 密钥
- 组织 ID

### 6.4 如何申请提高限制？

如需提高 API 调用限制，可以：

1. 升级到更高级别的用户计划
2. 提供使用数据证明需要更高限制
3. 联系客户支持申请临时提升配额
