# IM 业务场景下的术语表

## 通信基础概念

### 会话类型

- **单聊（One-to-One Chat/Private Chat）**：一对一的私密对话形式，类似微信私聊
- **群聊（Group Chat）**：支持多人参与的群组对话，成员数通常有限制（如 3000 人以内）
- **聊天室（Chatroom）**：无成员数限制的大型聊天空间，通常只有在线用户能收到消息
- **超级群（Ultra Group）**：类似 Discord 模式，支持无限成员、频道分组和用户群组的社区

### 消息类型

- **文本消息（Text Message）**：包含纯文本内容的消息
- **文件消息（File Message）**：包含图片、视频、音频等文件的消息
- **系统消息（Admin/System Message）**：系统发送的通知消息，通常无具体发送者
- **富媒体消息（Rich Message）**：包含额外互动元素的复合消息，如链接预览
- **临时消息（Ephemeral Message）**：不会被永久存储的一次性消息

## 身份与权限

- **用户 ID（User ID）**：用户在系统中的唯一标识符
- **成员（Member）**：加入群聊的用户
- **参与者（Participant）**：加入聊天室或开放频道的用户
- **管理员（Admin）**：拥有管理权限的用户
- **操作者（Operator）**：有权对频道、消息和用户进行管理的角色
- **封禁（Ban）**：将用户驱逐出频道并禁止其再次加入的操作
- **禁言（Mute）**：阻止用户在频道中发送消息的功能

## 消息功能

- **消息已读回执（Read Receipt）**：显示消息是否已被阅读的功能
- **消息送达回执（Delivery Receipt）**：确认消息是否成功投递的功能
- **表情反应（Reaction）**：使用表情符号对消息进行回应的功能
- **提及（Mention）**：在消息中特别标注某用户的功能
- **输入状态提示（Typing Indicator）**：显示其他用户正在输入消息的实时提示
- **消息撤回（Message Recall）**：撤回已发送消息的功能
- **消息编辑（Message Edit）**：修改已发送消息内容的功能
- **消息引用/回复（Quote Reply）**：引用先前消息并回复的功能
- **消息置顶（Message Pinning）**：将重要消息固定在对话顶部的功能
- **消息搜索（Message Search）**：在历史消息中搜索特定内容的功能

## 技术架构

- **即时通讯 SDK（IM SDK）**：提供即时通讯功能的软件开发工具包
- **UI 组件（UI Kit）**：预构建的用户界面组件，用于快速实现聊天功能
- **WebSocket**：用于实时双向通信的网络协议
- **推送通知（Push Notification）**：向离线用户发送消息提醒的机制
- **消息同步（Message Sync）**：确保多设备间消息一致性的机制
- **离线消息（Offline Message）**：用户离线期间的消息缓存和投递机制
- **消息云存储（Message Cloud Storage）**：在云端存储历史消息的服务
- **本地缓存（Local Cache）**：在用户设备上存储消息以提供离线访问能力

## 高级特性

- **消息流控（Smart Throttling）**：控制消息显示速度的技术
- **反垃圾机制（Anti-Spam）**：防止恶意用户发送大量重复消息的功能
- **内容审核（Content Moderation）**：过滤敏感内容和违规消息的功能
- **消息优先级（Message Priority）**：为不同消息设置优先级的功能
- **频道冻结（Channel Freeze）**：暂停频道内所有普通用户的发言权限
- **多终端同步（Multi-Device Sync）**：同步多个设备间消息和状态的功能
- **在线状态订阅（Online Status Subscription）**：获取用户在线状态的功能
- **实时音视频通话（RTC Call）**：在 IM 系统中集成音视频通话能力

## 安全与隐私

- **端到端加密（End-to-End Encryption）**：确保消息只能被发送者和接收者解读
- **文件加密（File Encryption）**：保护共享文件安全的加密机制
- **访问令牌（Access Token）**：用于验证用户身份的安全凭证
- **API 令牌（API Token）**：用于服务端 API 调用的安全凭证
- **数据合规（Compliance）**：符合各地区数据保护法规的措施

## 运营与分析

- **每日活跃用户（DAU）**：每日连接服务器的独立用户数量
- **每月活跃用户（MAU）**：每月连接服务器的独立用户数量
- **峰值并发连接（Peak Concurrent Connections）**：系统同时支持的最大连接数
- **高级分析（Advanced Analytics）**：提供用户行为和系统性能分析的工具
- **消息导出（Message Export）**：将消息历史导出为 CSV 或 JSON 格式的功能

## 集成与扩展

- **Webhook**：将事件实时同步到开发者服务器的机制
- **自定义消息类型（Custom Message Type）**：开发者自定义的特殊消息格式
- **频道元数据（Channel Metadata）**：存储频道附加信息的键值对
- **用户元数据（User Metadata）**：存储用户附加信息的键值对
- **频道集合（Channel Collection）**：用于构建频道列表视图的数据结构
- **消息集合（Message Collection）**：用于构建消息列表视图的数据结构

总结：

- 收录最核心的业务概念，例如：什么是超级群，超级群的特征表述，什么是聊天室，聊天室的特征是什么
- 收录可能存在误解和混淆的内容。例如：targetId, 用户A和用户B聊天，他们各自的targetId是对方的userId。
- 收录不常见，不能望文知义的内容。例如：不落地通知。
- 收录客户不直接使用，但是需要知道业务流转的内容。例如：全量消息路由。


难点：

- 面对多种读者：开发者、使用者、体验者、设计者等角色，背景知识阅读层面也不相同
- 多领域整合：有些术语涵盖内容很广。例如：加密：其实它是的每一种加密算法实现和使用都完全不同，每一种都有自己的概念和使用场景。
- 歧义、混用、认知对齐：很多余术语可能由于历史、文化、其他领域也有等因素，导致对于术语的理解不一致。
- 环境场景：任何术语都作用域某一个场景条件下，否则，很容易出现实际效果不一致。例如：客户提交工单说不能发送消息，这个问题的原因那就太多了，不具体指定操作步骤，使用环境，我们几乎无从判断。
- 技术依赖：某些术语可能仅仅是读者直接面对的冰山一角，下面还有一堆陌生的专业的概念需要理解，才能够理解当前的术语。这种复杂的术语更不容易理解和掌握。rtc里面的每一个环节和流程都有很多技术作为支撑。
- 时效性：某些术语会随着时间而发生改变。例如：群聊，刚开始仅仅是文字交流、后面增加了多媒体交流、添加了更加复杂的业务化场景。

建议：

- 提供基础的核心的术语，从各个维度进行描述完善
- 提供容易混淆的术语，减少重复的解释
